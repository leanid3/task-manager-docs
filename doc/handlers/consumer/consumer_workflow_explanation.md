# Отчет: Работа текущего consumer в системе Kafka

## Введение

В этом отчете объясняется, как работает текущий consumer (обработчик сообщений) в системе Kafka, в какой последовательности вызываются компоненты и зачем они нужны.

## Общая архитектура

Система обработки сообщений Kafka построена по модульной архитектуре с четким разделением ответственности между компонентами.

## Последовательность обработки сообщения

### 1. Прием сообщения
- **Компонент**: `KafkaMessageHandler`
- **Вызов**: `Handle(ctx context.Context, msg *kafka.Message)`
- **Назначение**: Принимает входящее сообщение из Kafka и передает его в реестр обработчиков
- **Что делает**: Логирует получение сообщения (топик, партиция, оффсет) и вызывает `registry.Handle()`

### 2. Маршрутизация сообщения
- **Компонент**: `Registry`
- **Вызов**: `Handle(ctx context.Context, msg *kafka.Message)`
- **Назначение**: Находит подходящий обработчик для топика сообщения
- **Что делает**: 
  - Получает название топика из сообщения
  - Ищет зарегистрированный обработчик для этого топика
  - Вызывает метод `Handle` найденного обработчика

### 3. Валидация сообщения
- **Компонент**: `Route[T]` → вызывает `validator(msg)`
- **Назначение**: Проверяет корректность формата сообщения и извлекает данные
- **Что делает**:
  - Вызывает функцию валидации, которая проверяет:
    - Формат ключа сообщения (TaskID)
    - Наличие и корректность заголовков (Status, WorkerID, TraceID)
    - Валидность содержимого сообщения (Value)
  - Возвращает типизированный объект с валидными данными

### 4. Обработка бизнес-логики
- **Компонент**: `Route[T]` → вызывает `useCase(ctx, validatedData)`
- **Назначение**: Выполняет основную бизнес-логику, связанную с сообщением
- **Что делает**:
  - Передает валидированные данные в соответствующий use case
  - Выполняет действия, предусмотренные бизнес-логикой (например, обновление статуса задачи)

### 5. Логирование результата
- **Компонент**: `Route[T]`
- **Назначение**: Логирует результат обработки
- **Что делает**:
  - Если произошла ошибка валидации - логирует ошибку валидации
  - Если произошла ошибка в бизнес-логике - логирует ошибку use case
  - Если все успешно - логирует успешную обработку

## Пример: Обработка статуса LLM задачи

### 1. Регистрация обработчика
- В `workflows/llm/task_llm.go` регистрируется маршрут для топика "tasks_llm"
- Указывается валидатор `TaskLLMValidator` и use case функция `UpdateTaskStatus`

### 2. Валидация LLM сообщения
- `TaskLLMValidator.Validate()` вызывает базовую валидацию
- `BaseValidator.ValidateContract()` проверяет:
  - Корректность TaskID в ключе сообщения
  - Наличие и валидность заголовков (Status, WorkerID, TraceID)
- Затем валидируется специфичный payload (результат или ошибка)

### 3. Обновление статуса задачи
- Вызывается `usecase.UpdateTaskStatus()` с валидированными данными
- В зависимости от статуса (PROCESSING, COMPLETED, FAILED) обновляется состояние задачи в базе данных

## Назначение каждого компонента

### Registry (Реестр)
- **Цель**: Централизованное управление обработчиками по топикам
- **Польза**: Позволяет легко добавлять новые типы сообщений без изменения основной логики

### Route[T] (Маршрут)
- **Цель**: Унифицированный шаблон обработки сообщений
- **Польза**: Обеспечивает одинаковую последовательность: валидация → бизнес-логика → логирование

### BaseValidator (Базовый валидатор)
- **Цель**: Проверка общих элементов контракта (ключ, заголовки)
- **Польза**: Предоставляет переиспользуемую логику валидации для всех типов сообщений

### HeaderExtractor (Извлекатель заголовков)
- **Цель**: Парсинг и валидация заголовков Kafka сообщения
- **Польза**: Централизованная логика извлечения заголовков с единообразной обработкой ошибок

### TaskLLMValidator (Специфический валидатор)
- **Цель**: Валидация специфичного содержимого для LLM задач
- **Польза**: Расширяет базовую валидацию специфичной логикой для конкретного типа сообщений

## Преимущества такой архитектуры

1. **Типобезопасность**: Использование generics обеспечивает типобезопасность на этапе компиляции
2. **Переиспользуемость**: Общие компоненты могут использоваться для разных типов сообщений
3. **Легкость расширения**: Простое добавление новых типов сообщений
4. **Единообразие**: Все сообщения обрабатываются по одному шаблону
5. **Тестируемость**: Каждый компонент может быть протестирован отдельно
6. **Логирование**: Единый подход к логированию на всех уровнях

## Заключение

Текущая архитектура consumer реализует грамотно спроектированную систему обработки сообщений Kafka с четким разделением ответственности, типобезопасностью и возможностью легкого расширения. Каждый компонент выполняет свою конкретную роль в цепочке обработки сообщений, обеспечивая надежность и поддерживаемость системы.
