# Документация по тестированию для сервиса Task Manager

## Обзор

Этот документ описывает стратегию тестирования, инструменты и процедуры для сервиса Task Manager. Task Manager - это микросервис на Go, который служит точкой доступа к API для внешних сервисов, управляет распределением задач между рабочими узлами через Kafka и собирает результаты от рабочих узлов.

## Стратегия тестирования

Сервис Task Manager следует комплексной стратегии тестирования, основанной на принципе пирамиды тестирования:

- **Модульные тесты**: Тестируют отдельные функции, методы и бизнес-логику в изоляции
- **Интеграционные тесты**: Тестируют взаимодействие между несколькими компонентами и внешними системами
- **Сквозные (E2E) тесты**: Тестируют полные рабочие процессы приложения от API до базы данных/хранилища
- **Инфраструктурные тесты**: Тестируют подключение и работу с внешними сервисами

## Типы тестов и расположение

### Модульные тесты
Расположены рядом с тестируемым кодом (например, файлы `*_test.go`):
- Сущности домена и их методы
- Функции вариантов использования
- Вспомогательные функции
- Функции валидации
- Функции обработки ошибок

### Интеграционные тесты
Расположены в каталоге `/test/integration/`:
- Интеграция репозитория и варианта использования
- Конечные точки API с замоканными внешними зависимостями
- Функциональность адаптера базы данных
- Функциональность адаптера хранилища
- Интеграция продюсера/консьюмера Kafka

### Сквозные тесты
Расположены в каталоге `/test/e2e/` (планируется):
- Полный жизненный цикл задачи (создать → обработать → получить результат)
- Тестирование потоков API
- Согласованность данных между компонентами

## Запуск тестов

### Использование скрипта запуска тестов

Проект включает удобный скрипт запуска тестов, который предоставляет удобочитаемый вывод:

```bash
# Запустить модульные тесты
./scripts/test-runner.sh unit

# Запустить интеграционные тесты
./scripts/test-runner.sh integration

# Запустить все тесты
./scripts/test-runner.sh all

# Запустить тесты вариантов использования
./scripts/test-runner.sh usecase

# Запустить тесты домена
./scripts/test-runner.sh domain

# Запустить тесты обработчиков
./scripts/test-runner.sh handlers

# Запустить тесты инфраструктуры
./scripts/test-runner.sh infrastructure
```

### Генерация отчетов о покрытии

```bash
# Сгенерировать отчет о покрытии для всех пакетов
./scripts/test-runner.sh coverage

# Сгенерировать отчет о покрытии для конкретного пакета
./scripts/test-runner.sh coverage ./internal/usecase/

# Запустить тесты с покрытием
./scripts/test-runner.sh coverage-run
```

### Запуск конкретных тестов

```bash
# Запустить конкретный тест по имени
./scripts/test-runner.sh run TestCreateTask

# Запустить конкретный тест в конкретном пакете
./scripts/test-runner.sh run TestUnifiedTaskUC_CreateTask ./internal/usecase/
```

### Список доступных тестов

```bash
# Перечислить все доступные тесты
./scripts/test-runner.sh list

# Перечислить тесты в конкретном пакете
./scripts/test-runner.sh list ./internal/entity/
```

### Использование стандартных команд Go

Вы также можете запускать тесты с помощью стандартных команд Go:

```bash
# Запустить все модульные тесты
go test ./internal/... -short

# Запустить все тесты, включая интеграционные
go test ./...

# Запустить тесты с подробным выводом
go test ./... -v

# Запустить тесты с покрытием
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out -o coverage.html

# Запустить конкретный тест
go test ./internal/usecase/ -run TestCreateTask -v
```

## Структура и соглашения тестов

### Структура модульных тестов

Модульные тесты следуют шаблону таблицы тестов:

```go
func TestTaskUCCreateTask(t *testing.T) {
    tests := []struct {
        name          string
        reader        io.Reader
        filename      string
        filesize      int64
        requestID     string
        setupMocks    func(*mocks.MockRepository, *mocks.MockProducer, *mocks.MockStorageRepository, *mocks.Logger)
        expectedError bool
        errorCode     apperrors.ErrorCode
    }{
        // Тестовые случаи
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            // Реализация теста
        })
    }
}
```

### Стратегия мокирования

Проект использует `github.com/stretchr/testify/mock` для мокирования интерфейсов:
- Создавайте повторно используемые реализации моков в `/test/mocks/`
- Поддерживайте последовательное поведение моков в тестах
- Четко документируйте ожидания моков

### Соглашение об именовании
- Модульные тесты: `{функциональность}_test.go` находятся вместе с кодом
- Интеграционные тесты: `{компонент}_integration_test.go`
- E2E тесты: `{рабочий_процесс}_e2e_test.go`

## Контрольные точки качества

### Требования к покрытию
- Минимум 80% покрытия кода для новых функций
- Нет снижения общего процента покрытия
- Критические пути должны иметь покрытие 95%+

### Требования к тестам
- Все тесты должны быть детерминированными
- Правильная очистка для предотвращения утечки ресурсов
- Нулевое количество нестабильных тестов в CI

## Управление тестовыми данными

- Используйте фабричные функции для создания тестовых данных
- Реализуйте процедуры очистки для удаления тестовых данных
- Используйте уникальные идентификаторы для предотвращения помех между тестами
- Рассмотрите возможность использования тестовых контейнеров для внешних зависимостей

## Устранение распространенных проблем

### Ошибки компиляции в тестах
Если вы сталкиваетесь с ошибками компиляции при запуске тестов, проверьте:
- Корректность операторов импорта
- Все методы интерфейса реализованы в моках
- Зависимости правильно замоканы

### Ошибки интеграционных тестов
Интеграционные тесты могут завершаться с ошибкой из-за:
- Отсутствия внешних сервисов (PostgreSQL, Kafka, MinIO)
- Неправильной конфигурации
- Проблем с сетью

### Проблемы с производительностью
Если тесты работают медленно:
- Проверьте ненужные вызовы внешних сервисов
- Обеспечьте надлежащую очистку для предотвращения утечки ресурсов
- Рассмотрите возможность параллельного выполнения тестов, где это уместно

## Добавление новых тестов

При добавлении новой функциональности:

1. Напишите модульные тесты для новой бизнес-логики
2. Добавьте интеграционные тесты для взаимодействия компонентов
3. Обновите существующие тесты, если изменяются интерфейсы
4. Убедитесь, что новые тесты соответствуют требованиям к покрытию
5. Запустите все тесты, чтобы убедиться, что ничего не сломалось

## Интеграция CI/CD

Стратегия тестирования интегрирована в конвейер CI/CD:
- Модульные тесты запускаются при каждом коммите
- Интеграционные тесты запускаются при запросах на слияние
- Генерируются и проверяются отчеты о покрытии
- Сравниваются эталонные показатели производительности
